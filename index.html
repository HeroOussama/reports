FWF v2/features Traffic Spike

~500% Increase in v2/features Requests

Investigating

Starting July 7, when the release containing PR #11955 (Android tag 8.0.287-1503) reached 100% rollout, the FWF backend reported a ~500% increase in v2/features requests, peaking around 12:00 UTC.

About v2/features: Called by the FWF SDK whenever the app fetches feature-flag variations. Each fetch is wrapped in a Sentry health span (fwf_delivery_health) tagged with fwf.source and fwf.success outcome.
Hypothesis (Initial)
PR #11955 was a crash fix ("FwfHelper.getVariations"). Its key change ensures the FWF SDK singleton always has a valid Android context. In FWF SDK v5.5.4, network calls to v2/features are gated by a check that fails when context is null. The hypothesis is that before the fix, fetches were silently dropped when context was missing, and the fix "unblocked" these — converting previously-dropped calls into real backend requests without adding new call sites.
Open Items / Next Steps:
  1. Break down backend v2/features increase by platform (iOS vs Android) and app_version — platform attribution must be confirmed
  2. Overlay the backend request curve with the rollout curve of 8.0.287-1503 — true causation would track adoption %, not a single flat step
  3. Review the full changeset of tag 8.0.287-1503 (all commits, not just PR #11955) for a more likely culprit
Data Sources: PR #11955 diff + FWF SDK v5.5.4 source (Gradle cache) · Sentry Explore → Traces, span.op:fwf_delivery_health (90-day + Jun 20–Jul 15 exports)
